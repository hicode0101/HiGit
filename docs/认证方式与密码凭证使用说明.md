## 1. 什么时候需要认证

对远端仓库执行 **克隆 / 推送 / 拉取 / 抓取** 时，如果远端需要身份验证（私有仓库，或对公开仓库有写操作），HiGit 会发起认证。认证方式由远端 URL 决定，**无需手动指定类型**：

| 远端 URL 形式 | 认证方式 | 用户名推断 |
|---|---|---|
| `https://github.com/用户名/仓库.git` | HTTPS：用户名 + 密码/Token | 自动取路径首段（如 `github.com/hicode0101/...` → `hicode0101`） |
| `git@github.com:hicode0101/仓库.git` | SSH：密钥 | 固定 `git` |
| `ssh://user@host/path` | SSH：密钥 | `@` 前的用户名，缺省 `git` |

在克隆对话框或仓库设置中修改 URL 时，认证页签会**自动切换**并预填用户名。

认证信息可以在三处提供（优先级从高到低，详见 §5）：

1. 同步 / 克隆对话框的"认证"页签（当次生效）；
2. 仓库设置（该仓库长期生效）；
3. 认证失败时弹出的凭证对话框（临时补录，提交后原地重试）。

## 2. HTTPS：用户名 + 密码（Token）

### 2.1 填写方法

在认证页签选择 HTTPS 后填写**用户名**与**密码**。对 GitHub 等托管平台，密码栏填 **Personal Access Token（PAT）** 而非账号密码——GitHub 已不接受账号密码推拉代码。

### 2.2 "记住凭证"

勾选 **"记住到系统凭证管理器"** 后，凭证写入操作系统的安全存储，下次同步自动携带（首次请求即带上，不再等 401 挑战）：

| 操作系统 | 存储位置 | 条目名 |
|---|---|---|
| Windows | 凭证管理器（控制面板 → 凭证管理器 → Windows 凭据） | `git:https://用户名@host` 形式由系统生成，服务名为 **HiGit** |
| macOS | 钥匙串访问（Keychain Access） | `HiGit` |
| Linux | Secret Service（GNOME Keyring / KWallet） | `HiGit` |

- **配置文件里永远没有密码**：`config.json` 只保存用户名、密钥路径等非敏感字段；
- 密码输入框**不回显**已保存的密码；仓库设置中显示"已保存"徽章时，密码留空表示保持不变；
- 取消勾选并清空密码后保存，会**删除**已存的凭证条目。

### 2.3 凭证失效

使用"记住的凭证"被远端拒绝时，HiGit 会自动重试一次；仍失败则**自动删除这条失效凭证**并弹出凭证对话框让你重新输入——不会陷入用坏凭证反复失败的循环。

## 3. SSH：密钥认证

### 3.1 HiGit 的 SSH 认证链

SSH 认证按固定顺序尝试三级，日志中可看到每一步（同步对话框"认证："行）：

```
① 显式配置的密钥（仓库设置 / 对话框里选的密钥文件）
        ↓ 未配置、或格式不受支持（日志会给出原因）
② ssh-agent（Windows 上真正可用的是 Pageant，见 §3.4）
        ↓ agent 不可用或拒绝
③ ~/.ssh 默认密钥：依次尝试 id_ed25519 → id_ecdsa → id_rsa
```

### 3.2 密钥格式约束（重要）

HiGit 的 Git 引擎在不同平台使用不同的加密后端，**能直接解析的私钥文件格式**如下：

| 私钥文件格式 | 文件头 | Windows | macOS / Linux |
|---|---|---|---|
| PKCS#1 PEM（RSA / DSA） | `-----BEGIN RSA PRIVATE KEY-----` | ✅ 直接可用 | ✅ |
| OpenSSH 容器（含 ed25519） | `-----BEGIN OPENSSH PRIVATE KEY-----` | ⛔ 跳过 | ⛔ 跳过* |
| PKCS#8 | `-----BEGIN PRIVATE KEY-----` | ⛔ 跳过 | ⛔ 跳过* |
| EC 私钥 | `-----BEGIN EC PRIVATE KEY-----` | ⛔ 跳过 | ⛔ 跳过* |
| PuTTY | `PuTTY-User-Key-File ...` | ⛔ 跳过 | ⛔ 跳过* |

\* 为保证全平台行为一致，HiGit 统一按文件头嗅探并跳过这些格式，日志会提示"请转换为 PEM 格式（RSA / DSA）"。

**被跳过的密钥不会让任务直接失败**——HiGit 会继续尝试 ssh-agent 和默认密钥；只有三级全部被远端拒绝才报"所有验证方式均被远端拒绝"。

### 3.3 把密钥转成可用格式（PKCS#1）

**方法一：openssl 转换**（OpenSSL 3.x 必须加 `-traditional`，否则输出的还是 PKCS#8）：

```bash
openssl rsa -in 原钥匙.pem -out 新钥匙.pem -traditional
# 验证文件头应为：-----BEGIN RSA PRIVATE KEY-----
```

**方法二：ssh-keygen 原地转换**（会改写原文件，注意备份）：

```bash
ssh-keygen -p -m PEM -f 原钥匙文件
```

**方法三：PuTTY .ppk 用户**——用 PuTTYgen 打开 .ppk，菜单 `Conversions → Export OpenSSH key` 之后再用方法二转 PEM；或直接在 PuTTYgen 里另存为传统 PEM。

转换后到 GitHub 账户的 SSH Keys 里确认对应公钥已注册（同一把钥匙转换格式前后公钥不变，无需重新注册）。可用命令行自测：

```bash
ssh -i 你的密钥 -o IdentitiesOnly=yes -T git@github.com
# 返回 "Hi 用户名!" 即钥匙与注册都正常
```

### 3.4 SSH Agent：ssh-agent 与 Pageant

**Agent 是什么**：SSH agent 是常驻后台的"密钥保管员"。私钥解锁后载入 agent 内存，SSH 客户端把签名请求转交给它完成，会话过程中私钥文件本身不再参与。对 HiGit 的价值：**签名发生在 agent 进程里，绕开 §3.2 的文件格式限制——任何格式的密钥（含 ed25519、EC、.ppk）放进 agent 都能被 HiGit 使用**，也不需要在 HiGit 里填写密钥口令。

#### 两种 agent 的介绍

**ssh-agent**：OpenSSH 的标准 agent，Unix/macOS 世界的标配。Windows 10/11 内置了它的移植版，以 Windows 服务形式运行（默认禁用），密钥用 `ssh-add.exe` 添加并持久保存。

**Pageant**：PuTTY 套件的认证代理（PuTTY Authentication Agent），一个托盘常驻小程序。它管理 PuTTY 专用的 `.ppk` 密钥文件（PuTTYgen 可从任意格式导入转换），通过 Windows 窗口消息（WM_COPYDATA）与客户端通信，不占用网络端口。

#### 对比

| | ssh-agent | Pageant |
|---|---|---|
| 所属套件 | OpenSSH | PuTTY |
| Windows 形态 | 系统服务 `ssh-agent`（默认禁用）+ `ssh-add.exe` | 托盘程序 `pageant.exe`，手动或开机启动 |
| macOS / Linux | 标配（`SSH_AUTH_SOCK`） | 一般不使用 |
| 原生密钥格式 | OpenSSH 容器 / PEM（含 ed25519） | `.ppk`（PuTTYgen 从任意格式导入转换） |
| 密钥持久化 | Windows 版跨重启保留 | 默认不持久，通常用启动项自动加载 |
| 与客户端通信 | Unix socket / Windows 命名管道 | WM_COPYDATA 窗口消息 |
| **HiGit 实际支持** | ✅ macOS / Linux ｜ ⛔ Windows（见下） | ✅ Windows |

#### HiGit 在 Windows 上的实际行为（探测和连接是两层）

- **探测层**（决定认证链里是否包含"尝试 ssh-agent"这一步）：HiGit 检测到 Windows OpenSSH agent 的命名管道 `\\.\pipe\openssh-ssh-agent` **或** Pageant 主窗口存在，都会把 Agent 步骤放进认证链；
- **连接层**（真正用 agent 签名）：HiGit 引擎使用的 libssh2 在 Windows 上**只实现了 Pageant 一种 agent 传输**。因此：
  - **Pageant 在运行 → Agent 步骤真正可用**（Windows 上推荐的 agent 方案）；
  - 只有 Windows 内置 OpenSSH agent 服务在跑 → 链路会包含 Agent 步骤，但连接失败、日志显示"ssh-agent 被远端拒绝"，随后继续尝试默认密钥——无害，但这一步不会产生效果；
- 结论：**Windows 上想让 HiGit 走 agent，请使用 Pageant**；Windows 内置 OpenSSH agent 服务对命令行 `ssh` / `git` 等工具仍然有价值，只是对 HiGit 不生效。

#### Pageant 使用步骤（Windows 推荐）

1. 安装 PuTTY（或单独下载 `pageant.exe` / `puttygen.exe`）；
2. 用 **PuTTYgen** 把现有私钥导入并另存为 `.ppk`：菜单 `Conversions → Import key`（支持从 OpenSSH 容器 / PKCS#8 / PKCS#1 导入）→ `Save private key`；
3. 运行 Pageant → 托盘图标右键 → **Add Key** 选择 `.ppk`（带口令的会提示输入一次，之后会话内免口令）；
4. 开机自动加载：创建快捷方式 `pageant.exe D:\keys\xxx.ppk D:\keys\yyy.ppk` 放入启动文件夹（`Win+R` → `shell:startup`）；
5. 验证：在 HiGit 里重新拉取，认证日志应出现"认证： 尝试 ssh-agent"并紧跟"认证通过： ssh-agent"。

#### 使用 ssh-agent（macOS / Linux）

agent 随桌面环境或 `ssh-agent` shell 启动（HiGit 通过 `SSH_AUTH_SOCK` 检测），`ssh-add 私钥` 添加即可，OpenSSH 容器格式的 ed25519 密钥也可以直接添加。

**Windows 内置 OpenSSH agent 的启用方法**（供命令行工具使用，对 HiGit 无效，仅供参考）：

```powershell
# 管理员 PowerShell
Set-Service ssh-agent -StartupType Automatic
Start-Service ssh-agent
# 添加密钥（必须用系统自带 ssh-add.exe，Git Bash 自带的看不到该服务）
C:\Windows\System32\OpenSSH\ssh-add.exe D:\路径\私钥
```

### 3.5 使用 ~/.ssh 默认密钥

不配置密钥、也没有 agent 时，HiGit 依次尝试 `~/.ssh/id_ed25519`、`id_ecdsa`、`id_rsa`。结合 §3.2，Windows 上实际可用的默认密钥是 **PKCS#1 格式的 `id_rsa`**：

```bash
cp /d/RSA_DSA/github_id_rsa_4096_hicode0101_pkcs1.pem ~/.ssh/id_rsa
cp /d/RSA_DSA/github_id_rsa_4096_hicode0101.pub   ~/.ssh/id_rsa.pub
```

Windows 还需收紧文件权限（权限过宽 OpenSSH 会拒用）：

```
icacls "C:\Users\<你的用户名>\.ssh\id_rsa" /inheritance:r /grant:r "<你的用户名>:F"
```

注意：`id_rsa` 会成为本机所有 ssh 工具的默认钥匙；只想对 GitHub 生效的话改用 `~/.ssh/config`：

```
Host github.com
    IdentityFile ~/.ssh/id_rsa
```

### 3.6 密钥口令（Passphrase）

- 认证页签 / 凭证对话框中的 **Passphrase** 字段用于"配置密钥"路径下带口令的 PKCS#1 密钥；
- 通过 ssh-agent 使用密钥时不需要在 HiGit 里填口令（agent 解锁后自动签名）。

## 4. 主机指纹校验（防中间人）

首次通过 SSH 连接新主机时，HiGit 采用 **TOFU（Trust On First Use）**策略：记录该主机指纹到 `~/.ssh/known_hosts`（与 OpenSSH 命令行共用同一文件），此后每次连接校验。

- 指纹一致 → 正常放行；
- 指纹**变更** → 直接拒绝连接（提示主机密钥不匹配）。若确认是对方服务器正常换钥匙（重装/迁移），手动删除 `~/.ssh/known_hosts` 中对应行即可恢复。

支持 `git@host:path`（22 端口）与 `ssh://user@host:port/path`（非 22 端口）两种远端写法。

## 5. 认证优先级与重试机制（总览）

```
发起同步/克隆
   │
   ├─ 对话框/任务显式携带的凭证（当次输入）
   ├─ keyring 预取（host 命中"记住的凭证"则随首个请求携带）
   │
   ▼ 被远端拒绝（AuthFailed）
弹出凭证对话框（显示 host / 认证方式 / 用户名）
   │  用户补录 + 可勾选"记住"
   ▼
原地重试同一任务（无需重新发起）
   │  若重试用的是记住的凭证且再次失败
   ▼
自动删除失效凭证条目，任务报错（错误详情可复制）
```

SSH 的三级链（§3.1）发生在每一轮"交给远端的凭证"内部：配置密钥 → agent → 默认密钥，日志逐级显示尝试与拒绝。

## 6. 常见问题排查

**Q1：日志出现"PKCS#8 格式不受当前引擎支持，请转换为 PEM 格式（RSA / DSA）"？**
你的密钥是 PKCS#8（文件头 `BEGIN PRIVATE KEY`）。按 §3.3 转换为 PKCS#1（`BEGIN RSA PRIVATE KEY`）。注意 OpenSSL 3.x 转换要加 `-traditional`。

**Q2：提示"所有验证方式均被远端拒绝"？**
按顺序排查：① 配置的密钥格式是否被跳过（看"认证："行原因文案）；② Windows 上确认 **Pageant** 在运行且已加载密钥（内置 OpenSSH agent 服务对 HiGit 不生效，见 §3.4）；macOS / Linux 确认 agent 运行且已 `ssh-add`；③ `~/.ssh` 是否有格式正确且已注册公钥的默认密钥；④ 用命令行 `ssh -i 密钥 -T git@github.com` 验证钥匙与 GitHub 注册本身是否正常。

**Q3：HTTPS 推送一直 401 / 403？**
GitHub 必须用 PAT 而非账号密码；确认 token 勾选了 repo（或细粒度的对应仓库）权限；组织仓库需确认 SSO 授权。

**Q4：换了服务器 / 重建了仓库后 SSH 连不上？**
若错误提示主机密钥不匹配，是 TOFU 防中间人机制生效（§4）——确认服务器变更合法后删除 `known_hosts` 对应行。

**Q5：代理环境下克隆/推送失败？**
设置 → 网络代理开启并填地址（如 `socks5://127.0.0.1:1080`，支持 `http(s)://`），作用于克隆 / 抓取 / 推送 / 拉取；关闭开关则直连。

**Q6：凭证"记住"了但没生效？**
确认勾选时任务最终成功过（失败凭证已被自动清理）；检查系统凭证管理器 / 钥匙串中 `HiGit` 条目是否存在；仓库远端 URL 变更（host 变了）后需要重新记住一次。

## 7. 安全说明

- 密码 / Token / SSH 口令**只存于系统凭证管理器**（Windows 凭证管理器 / macOS 钥匙串 / Linux Secret Service），应用配置文件与日志中不含任何秘密明文；
- 密码输入框一律不回显；"已保存"仅以徽章提示状态；
- SSH 主机指纹变更即硬拒绝，防止中间人攻击；
- "打开官网链接"等外部跳转仅允许 http/https。
