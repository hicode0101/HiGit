## 1. 环境要求

| 依赖 | 版本 | 说明 |
|---|---|---|
| Rust | **1.85+**（edition 2024） | 工具链含 `cargo`；无需额外目标（交叉编译目标由 CI 安装） |
| Node.js | 18+（CI 用 22） | 仅用于前端构建 |
| pnpm | 10 | 前端包管理器（`packageManager` 字段锁定） |
| Git 命令行 | **不需要** | libgit2 静态链接，运行与构建均不依赖系统 Git |
| 系统库 | Linux 需 webkit2gtk 等 | 仅 Linux 开发环境：`libwebkit2gtk-4.1-dev build-essential curl wget file libxdo-dev libssl-dev libayatana-appindicator3-dev librsvg2-dev`（CI 中自动安装） |

平台备注：构建无需本机安装 OpenSSL——三平台均由 `vendored-openssl` 从源码静态编译（Windows 构建需要 Perl，如 Strawberry Perl；NASM 可选，缺失时自动 no-asm；Unix 上同时满足 macOS Intel 交叉编译找不到系统 OpenSSL 的问题）。

## 2. 获取与首次构建

```bash
git clone git@github.com:hicode0101/HiGit.git
cd HiGit
pnpm install          # 安装前端依赖（--frozen-lockfile 在 CI 中使用）
```

## 3. 本地开发运行

```bash
pnpm tauri dev
```

- 等价于先执行 `pnpm dev`（Vite dev server，监听 `http://127.0.0.1:1420`），再启动 Tauri 壳；
- Rust 代码改动会自动重编译重启；前端改动热更新；
- **Windows 端口注意**：若 1420 被系统保留端口段占用（`netsh interface ipv4 show excludedportrange protocol=tcp` 可查），会报 `listen EACCES`，需在 `vite.config.ts` 与 `src-tauri/tauri.conf.json`（`devUrl`）同步改用其他端口；
- **网络注意**：Rust 依赖下载走 cargo；若 cargo 卡在本地代理（如 `127.0.0.1:7891`）报 `Could not connect to server`，说明 git 全局配置 `http.proxy` 指向的代理客户端没开——开启代理客户端或临时移除该配置。

## 4. 前端类型检查与构建

```bash
pnpm build            # = vue-tsc --noEmit && vite build
```

`vue-tsc` 保证前端类型零错误；产物输出到 `dist/`。CI 与 `tauri build` 都会自动执行此步（`beforeBuildCommand`）。

## 5. 测试

```bash
cargo test --workspace      # 全量 49 项
cargo test -p higit-git     # 仅引擎层（冒烟 28 + 单元 10）
cargo test -p higit-core    # 仅配置/凭证/gitignore（11）
```

测试构成（共 **49** 项，全部为 Rust 测试）：

| 模块 | 数量 | 覆盖内容 |
|---|---|---|
| git2 引擎冒烟 | 28 | 真实临时仓库上验证 status / stage / commit / amend / log / branch / merge / diff 等引擎方法 |
| 引擎单元测试 | 10 | 差异统计 3 · SSH 凭证链与密钥格式嗅探 6 · 凭证相等性 1 |

说明：SSH 格式嗅探测试覆盖 .ppk 被拒、OpenSSH 容器（ed25519）/ PKCS#8 / EC / PKCS#1 PEM RSA/DSA 通过的完整矩阵——修改认证链代码后必须全量回归。

## 6. 本地发布构建

```bash
pnpm tauri build
```

先自动执行 `pnpm build`，再编译 release（Rust profile：`lto = "thin"`、`strip = true`、`codegen-units = 1`），最后按 `tauri.conf.json` 的 `bundle.targets: "all"` 打包。产物位置：

| 平台 | 产物 | 路径 |
|---|---|---|
| Windows | `HiGit_1.0.0_x64-setup.exe`（NSIS）/ `.msi` | `target/release/bundle/nsis/`、`msi/` |
| macOS | `.app` / `.dmg` | `target/release/bundle/macos/`、`dmg/` |
| Linux | `.deb` / `.rpm` / `.AppImage` | `target/release/bundle/deb/` 等 |

本地构建不注入版本号同步（版本仍为 `tauri.conf.json` 中的当前值），正式版本号由 CI 的 tag 流程写入。

## 7. 自动发布（GitHub Actions）

### 7.1 触发与流程

推送 **`v x.y.z` 格式 tag**（如 `v1.2.3`）到 `hicode0101/HiGit` 即触发 `.github/workflows/release.yml`：

```
push tag v1.2.3
   └─► 四平台并行 job（fail-fast: false）
        ├─ checkout
        ├─ pnpm / Node 22 / Rust stable（macOS 同时装 aarch64 + x86_64 双目标）
        ├─ Linux：apt 安装 webkit2gtk 等系统依赖
        ├─ node scripts/sync-version.mjs 1.2.3     # 版本号写入三处源
        ├─ tauri-apps/tauri-action@v0 构建 + 上传
        │     （Windows: NSIS/MSI；macOS: 双架构 DMG；Linux: deb/rpm/AppImage）
        └─ 创建/复用 GitHub Release "HiGit v1.2.3" 并上传产物
```

### 7.2 版本号规则

- **只接受 `x.y.z` 纯数字三段式**（MSI 的 ProductVersion 不支持 `1.2.3-beta` 之类的预发布后缀）；
- `sync-version.mjs` 在不满足时立即失败，对应 job 会在第一步给出明确提示；
- 三处版本源：`src-tauri/tauri.conf.json`（安装包元数据与"关于"显示）、根 `Cargo.toml [workspace.package].version`（exe 程序集属性）、`package.json`（前端包版本）。

### 7.3 运维注意事项（实战沉淀）

1. **Release 创建竞态**：四个平台 job 并行构建、并行创建同一个 Release，偶发 `422 already_exists` 导致个别 job 失败（构建本身没有问题）。**处置**：在 Actions 页面对该 run 点 "Re-run failed jobs"——重跑时 Release 已存在，直接走"上传产物"路径。**根治方向**（未实施）：先用独立 job 预创建 Release，将 `releaseId` 传给各平台 tauri-action；
2. **macOS Intel 包交叉编译**：macos-latest 为 Apple Silicon 机器，x86_64 包在同一台机器上 `--target x86_64-apple-darwin` 交叉编译。依赖链中的 OpenSSL 已通过 `cfg(unix)` 统一 `vendored-openssl` 从源码编译（2026-10 修复的原始故障：runner 上只有 arm64 OpenSSL，openssl-sys 找不到 x86_64 库导致 exit 101）。修改 Unix 侧依赖后注意 Cargo.lock 是否需要同步 `openssl-src` 版本；
3. **构建时长**：Unix 平台因 vendored OpenSSL，冷构建多 2–3 分钟，属预期；rust-cache 会缓存依赖编译产物；
4. **发布验证**：Release 产物应为 9 个（双架构 DMG + 双架构 app.tar.gz、exe + msi、deb/rpm/AppImage）；安装包内版本号应与 tag 一致（"关于"对话框可核对）；
5. **失败排查入口**：Job 日志中先看 `Sync version from tag`（版本号合法性）与 `Build and upload release`（编译/上传）两步。

### 7.4 权限与凭据

工作流仅使用内置 `GITHUB_TOKEN`（`permissions: contents: write`，用于创建 Release 与上传产物），无外部 secrets。
